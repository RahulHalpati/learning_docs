# 06-5 · RDS: a real relational database

> **Level:** Intermediate · **Prerequisites:** [06-4 Observability: CloudWatch & Logs](04_cloudwatch_logs.md)
> **Time:** 25 min · **Verified:** 2026-09-01 (Floci latest; a real `postgres:16.3-alpine` engine, confirmed with a live `psycopg2` round-trip)

DynamoDB ([03-2](../03_core_services/02_dynamodb.md)) covers NoSQL. Most backend
apps — including whatever you build with the [FastAPI](../../fastapi_production_backend/)
or [FastAPI+SQL](../../fastapi_complete/) courses — run on a **relational**
database instead, and on AWS that's **RDS**: a managed Postgres/MySQL/MariaDB
instance AWS patches, backs up, and can fail over for you.

## This one is not a mock

Every other lesson so far has been careful to say "Floci creates the API object,
it doesn't run real infrastructure behind it." RDS is the exception worth
noticing: Floci provisions a **real Postgres container**
(`public.ecr.aws/lambda`-style official images) behind the API — same as Lambda
in [03-4](../03_core_services/04_lambda_apigateway.md). Verified end to end:

```bash
awslocal rds create-db-instance --db-instance-identifier linkstash-db \
  --db-instance-class db.t3.micro --engine postgres \
  --master-username postgres --master-user-password devpass123 \
  --allocated-storage 20
```

> **Needs the Docker socket**, exactly like Lambda — start `floci` with
> `-v /var/run/docker.sock:/var/run/docker.sock -u root` (see
> [01-2](../01_foundations/02_setup_and_first_service.md)) or this call fails.

```bash
awslocal rds describe-db-instances --db-instance-identifier linkstash-db \
  --query 'DBInstances[0].[DBInstanceStatus,Endpoint.Address,Endpoint.Port,Engine,EngineVersion]' --output text
```

Verified output: `available   172.17.0.2   7001   postgres   16.3`, and
`docker ps` shows a container literally named `floci-rds-db-...` running image
`postgres:16.3-alpine`.

## Connect and use it like any Postgres

Because it's real Postgres, any Postgres client works — `psql`, `psycopg2`,
SQLAlchemy, whatever your app already uses:

```python
import psycopg2
conn = psycopg2.connect(host="172.17.0.2", port=7001,
                         user="postgres", password="devpass123", dbname="postgres")
cur = conn.cursor()
cur.execute("CREATE TABLE links (id serial PRIMARY KEY, slug text UNIQUE, url text);")
cur.execute("INSERT INTO links (slug, url) VALUES (%s, %s);", ("abc123", "https://example.com"))
conn.commit()
cur.execute("SELECT slug, url FROM links WHERE slug = %s;", ("abc123",))
print(cur.fetchone())   # ('abc123', 'https://example.com')
```

Verified: this exact round-trip ran against the instance above and returned the
inserted row — a genuine SQL `INSERT`/`SELECT`, not a canned response.

## Why not just use DynamoDB for everything?

The honest comparison, since the capstone already picked DynamoDB:

| | DynamoDB | RDS (Postgres) |
|---|---|---|
| Query shape | Fast on your **exact** key/GSI design, awkward otherwise | Arbitrary `WHERE`/`JOIN`/aggregate queries |
| Scaling | Automatic, near-infinite | Vertical first, read replicas for reads |
| Ops | Zero — fully managed, no instance to patch | You size the instance; AWS patches/backs it up |
| Transactions | Limited (single-table, `TransactWriteItems`) | Full ACID, multi-table |
| Best for | Known access patterns, massive scale, serverless | Relational data, reporting, ad-hoc queries, joins |

Rule of thumb from the field: **default to RDS/Postgres** unless you have a
specific, known access pattern and scale that DynamoDB is actually built for.
Most teams reach for DynamoDB too early because "AWS-native NoSQL" sounds
modern, then rebuild relational queries badly on top of it.

## Real-application concerns this raises

- **Connection pooling.** A Lambda that opens a fresh Postgres connection per
  invocation exhausts RDS's connection limit under load — use **RDS Proxy** (a
  managed connection pooler AWS puts in front of RDS for exactly this) or a
  pooler library (`psycopg2` + `pgbouncer`-style pooling) for serverless
  callers. A long-running FastAPI process is fine with a normal pool
  (SQLAlchemy's default).
- **Secrets, not hardcoded passwords.** The password above is inline for the
  demo; a real app loads it from **Secrets Manager** ([06-1](01_secrets_and_ssm.md))
  — AWS can even auto-rotate it and update the secret for you.
- **Read replicas** scale reads horizontally without touching the writer — the
  RDS-native version of the read/write split you'd hand-build elsewhere.
- **Multi-AZ** gives you an automatic standby failover for the write instance —
  the availability half of "production-ready," separate from the scaling half.

## Access & IAM

Two auth paths: the traditional master username/password (what we used above),
or **IAM database authentication** — short-lived tokens instead of a static
password, generated by `rds generate-db-auth-token` and authorized by a normal
IAM policy (`rds-db:connect`). Prefer IAM auth for anything that can use it; it
means one less long-lived secret to rotate. Floci creates the instance and
accepts either; it doesn't enforce IAM either way ([02-1](../02_iam_and_access/01_access_model_iam_sts.md)).

## Recap & next

- ✅ **RDS** = a managed relational database; Floci backs it with a **real
  Postgres engine**, verified with a live SQL round-trip.
- ✅ Default to **RDS/Postgres** for relational data; reach for **DynamoDB**
  only when you have a specific access pattern it's built for.
- ✅ Production concerns beyond "it connects": **connection pooling** (RDS
  Proxy for serverless callers), **secrets in Secrets Manager**, **read
  replicas**, **Multi-AZ**.

## Exercise

Your FastAPI app on Lambda intermittently gets `too many connections` errors
from RDS under load, but the same code runs fine as a long-lived process on
EC2. Why the difference, and what's the fix?

<details>
<summary>Answer</summary>

Each Lambda **invocation** can spin up a fresh execution environment with its
own connection, and under concurrent load that's potentially hundreds of
simultaneous connections — RDS instances cap total connections (scales with
instance size), so Lambda's bursty concurrency model exhausts it fast. A
long-lived EC2 process keeps one pool of connections open and reuses them,
so it never gets close to the limit. Fix: put **RDS Proxy** in front of the
database — Lambda connects to the proxy, which multiplexes a much smaller
number of real connections to RDS.

</details>
