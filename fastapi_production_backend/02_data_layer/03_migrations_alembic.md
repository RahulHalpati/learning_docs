# 02-3 · Migrations with Alembic

> **Level:** Intermediate · **Prerequisites:** [02-1 · SQLAlchemy models](01_sqlalchemy_models.md)
> **Time:** 40 min · **Verified:** 2026-07-27 (alembic 1.18.5, SQLAlchemy 2.0.51)

## Why this matters

`Base.metadata.create_all()` is fine for a first run, but you can't `create_all` your way through a *live* database — you need to *change* an existing schema (add a column, an index, a table) without losing data. **Alembic** is version control for your schema: each change is a migration file you apply forward (`upgrade`) or roll back (`downgrade`).

> **Never use `create_all` in production.** It only creates missing tables — it can't alter existing ones, and it gives you no history or rollback. Migrations are the production path.

---

## Setup (async-aware)

Alembic's `migrations/env.py` is wired to read the URL from your settings and use the async engine, and to target `Base.metadata` (so autogenerate can compare):

```python
# migrations/env.py (essentials)
from app.core.config import settings
from app.db.base import Base
import app.models                          # register ALL models

config.set_main_option("sqlalchemy.url", settings.database_url)
target_metadata = Base.metadata

async def run_migrations_online():
    connectable = async_engine_from_config(..., poolclass=pool.NullPool)
    async with connectable.connect() as conn:
        await conn.run_sync(_do_run_migrations)   # bridge async → Alembic's sync API
```

`render_as_batch=True` is set so `ALTER TABLE` works on SQLite too (it recreates the table under the hood).

## Autogenerate a migration

Alembic diffs your **models** against the **current database** and writes the delta:

```bash
alembic revision --autogenerate -m "initial schema"
```

**Output (real run):**
```
INFO  [alembic.autogenerate.compare] Detected added table 'users'
INFO  [alembic.autogenerate.compare] Detected added index 'ix_users_email' on '('email',)'
INFO  [alembic.autogenerate.compare] Detected added table 'projects'
INFO  [alembic.autogenerate.compare] Detected added table 'tasks'
Generating .../migrations/versions/0576dd2868d7_initial_schema.py ... done
```

It found all three tables and their indexes and wrote a migration file with `upgrade()`/`downgrade()` functions.

> ⚠️ **Always read the generated migration.** Autogenerate is a *draft*, not gospel — it can miss some changes (e.g. a column *rename* looks like drop+add, which loses data) and occasionally proposes spurious diffs. Review every migration before committing it.

---

## Apply it

```bash
alembic upgrade head
```

**Output (real run):**
```
INFO  [alembic.runtime.migration] Running upgrade  -> 0576dd2868d7, initial schema
```

Confirm the tables exist:
```
['alembic_version', 'users', 'projects', 'tasks']
```

`alembic_version` is Alembic's bookmark — it records which migration the database is at, so `upgrade`/`downgrade` know what to run. The same commands work against **SQLite locally and Postgres in production** — the migration is portable.

---

## The everyday workflow

```bash
# 1. change a model (add a column, index, table)
# 2. generate the migration
alembic revision --autogenerate -m "add task due_date"
# 3. READ the generated file, adjust if needed
# 4. apply it
alembic upgrade head
# roll back the last one if wrong:
alembic downgrade -1
```

In deployment, migrations run **before** the new app version serves traffic — the TaskFlow container does exactly this: `alembic upgrade head && uvicorn ...` ([09-1](../09_containerization_and_deploy/01_dockerfile.md)).

> **Tip — one migration per change, committed with the code.** Migrations live in git next to the model change that caused them. Reviewers see the schema delta; teammates get it on `git pull`; deploys apply it automatically. A schema change without a migration is a production incident in waiting.

---

## Recap & next

- ✅ Alembic is version control for your schema: `revision --autogenerate` → **read** → `upgrade head`.
- ✅ It diffs models vs the DB; `alembic_version` tracks where the DB is; migrations are portable (SQLite ↔ Postgres).
- ✅ Never `create_all` in production; **always review** autogenerated migrations (renames look like drop+add).
- ✅ Commit migrations with the code; apply them before serving on deploy.
- ✅ Self-check: why is `alembic upgrade head` safe to run on every deploy, but `create_all` is not?

## Exercises

1. Add a `due_date` column to `Task`, autogenerate a migration, read it, and apply it. Then `alembic downgrade -1` and confirm the column is gone.

<details>
<summary>Solution</summary>

`alembic revision --autogenerate -m "add task due_date"` writes an `op.add_column("tasks", ...)`; `upgrade head` applies it; `downgrade -1` runs the generated `op.drop_column`. You just evolved the schema forward and back — with data preserved on the way up.
</details>
