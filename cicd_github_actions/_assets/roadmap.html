The idea that makes it click

CI runs the same commands you do

Every stage is a make target, so "works on my machine" and "works in CI" run identical commands from one source of truth. Verified in this environment:

make ci
$ ruff check app tests
All checks passed!
$ pytest
........                                        8 passed in 0.16s
$ coverage report --fail-under=80
TOTAL    51    1    98%
$ pip-audit -r requirements.txt
No known vulnerabilities found
✅ CI passed locally

CI vs CD

Integrate continuously · deliver deliberately

Continuous Integration

Every PR is auto-built, tested across a Python matrix, and scanned. A red check blocks the merge.
pull_request → lint · test · security

Continuous Delivery

Main is always deployable. Staging deploys automatically; production waits behind a required reviewer.
main → build → staging → approve → prod

Built on the other courses

The glue of the collection

This pipeline reuses what you already built — and leads into infrastructure.

# the security stage runs the audit course's tools
bandit -r app          # SAST  → Secure Code Audit course
pip-audit -r requirements.txt   # SCA

# the build stage produces the Docker course's image
docker build -t ghcr.io/org/linkstash:$SHA .

# next course: OpenTofu provisions the infra this deploys to
tofu apply     # → Infrastructure as Code

A green build is not a working deploy. Verifying this course, the app first bound to 127.0.0.1 inside the container and the published port couldn't reach it — the smoke test caught it. That check is why staging exists before production.
